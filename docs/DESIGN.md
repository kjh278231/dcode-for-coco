## 4. 요청 처리 흐름

1. **탐색.** 읽기 도구만 가진 서브에이전트가 저장소를 살피고 요약을 돌려준다.
2. **코드 변경 판정.** Jev J5가 요청과 탐색 요약을 받아 판정한다. 0이면 답변하고 끝낸다.
3. **계획 작성.** 주 에이전트가 계획 파일을 만든다 (5장).
4. **형식 검사와 내용 판정.** 코드가 frontmatter와 필수 절을 검사하고, Jev J1~J3이 내용을 판정한다.
5. **AI 리뷰.** LLM 리뷰어가 항상 수정 의견을 쓴다. Jev 결과를 입력으로 받는다. 리뷰와 수정 왕복은 최대 2회다.
6. **사람 질문.** 계획의 "미결 질문" 절이 비어 있지 않으면 사람에게 묻는다 (7장). 답은 "결정 사항" 절에 적고 리뷰를 다시 거친다.
7. **사람 승인.** 사람이 계획을 승인한다.
8. **코드 변경.** 승인 뒤에만 쓰기 도구가 열린다. 범위를 벗어나면 재검토로 돌아간다 (6장).
9. **테스트와 결과.** 계획의 `test_command`를 실행하고 결과를 기록한다.
10. **작업 기록과 관찰.** 작업 기록을 Memory에 저장하고 개선 관찰을 남긴다 (8장, 9장).

**비대화(`-n`) 실행.** 계획과 질문을 출력하고 끝낸다. 코드 변경 도구는 실행하지 않는다.
승인과 답은 호출하는 서비스가 이전 맥락과 함께 다시 호출해서 전달한다. 비대화는 주 사용 경로가 아니다.
dcode의 비대화 모드는 셸 외 도구에 사람 승인 처리기가 없다 (`Day09/TOOLS_REFERENCE.md:128`).

## 5. 계획 파일

- 위치: 작업 대상 프로젝트의 `.deepagents/plans/<id>.md`
- 형식: 마크다운과 YAML frontmatter. dcode의 서브에이전트 정의와 같은 형식이다
  (`deepagents_code/subagents.py:81`).
- 코드가 판정하는 값만 frontmatter에 둔다.

| 위치 | 항목 | 쓰임 |
|---|---|---|
| frontmatter | `status` | 승인 전 쓰기 차단 |
| frontmatter | `targets` (수정 대상 파일 경로 목록) | 범위 대조 |
| frontmatter | `test_command` | 테스트 실행과 기록 |
| 본문 | 요구사항, 작업 범위, 완료 조건, 작업 순서 | 평가 2-1, 2-2 |
| 본문 | 참고한 Memory | 평가 3-2. 없으면 "없음" |
| 본문 | 미결 질문, 결정 사항 | 사람에게 되묻기 |

- 본문의 필수 절은 "존재하고 비어 있지 않음"을 코드가 검사한다.
- 에이전트의 `write_file`, `edit_file`, `delete`는 이 폴더에 쓸 수 없다. 작성과 `status` 변경은 게이트 코드만 한다.
- `execute` 명령 문자열에 이 경로가 있으면 거부한다. 문자열 대조라서 완전하지 않다.
- 계획 파일과 Langfuse trace는 서로의 id를 적는다.

## 6. 게이트

게이트는 미들웨어가 들고 있는 단계 상태로 동작한다. 단계는 탐색, 계획, 리뷰, 승인 대기, 실행이다.

- 승인 전 단계에서는 쓰기 도구를 모델에게 보여주는 도구 목록에서 뺀다.
- 도구 호출 직전 검사를 마지막 방어로 둔다. 승인된 계획이 없으면 `write_file`, `edit_file`, `delete`를 거부한다.
- Jev J5가 틀려도 결과는 "거부되고 계획 단계로 돌아감"이다. 계획 없는 코드 변경은 일어나지 않는다.

**범위 대조 (승인 뒤).**

| 호출 | 판정 |
|---|---|
| 쓰기 경로가 `targets`에 정확히 있음 | 통과 |
| 쓰기 경로가 `targets`에 없음 | Jev J4. 1이면 통과하고 `targets`에 추가하며 기록한다. 0이면 재검토 |
| `execute` | Jev J4. 0이면 재검토 |
| 탐색 단계의 `execute` | 읽기 전용 명령만 허용. dcode의 기존 허용 규칙 재사용을 검토한다 (`deepagents_code/auto_mode.py:2571`) |

**Jev 질문.** 전부 `Noul`(0 또는 1)이다 (`Day04_new/cap_lab/decisions.py:27`).

| # | 질문 | 시점 |
|---|---|---|
| J1 | 완료 조건이 실행해서 확인할 수 있는 조건인가 | 계획 작성 직후 |
| J2 | 작업 범위가 요구사항을 벗어나지 않는가 | 계획 작성 직후 |
| J3 | 작업 순서와 테스트 방법이 수정 대상에 대응하는가 | 계획 작성 직후 |
| J4 | 이 쓰기 경로 또는 `execute` 명령이 승인된 계획 범위 안인가 | 도구 호출 직전 |
| J5 | 이 요청이 코드 변경을 필요로 하는가 | 탐색 직후 |
| J6 | 이 작업 기록이 이 요청에 해당하는가 | 요청 시작, 모델 호출 전 |

**보정.** 질문마다 보정 사례 묶음을 만든다. Sonnet급 모델이 사례를 만들고 Jev로 평가한 뒤 질문 문구를 고친다.

- 정답은 생성할 때 지정한다. 생성 뒤에 모델이 정답을 매기지 않는다.
- 문구를 고치는 묶음과 확인용 묶음을 나눈다.

## 7. 사람에게 되묻는 기준

작성자와 LLM 리뷰어의 지침에 같은 목록을 넣는다. 판단은 모델에 맡긴다.
원칙은 하나다. 저장소를 읽어 답이 나오면 묻지 않고, 답이 사용자에게만 있으면 묻는다.

| # | 물어야 하는 결정 |
|---|---|
| 1 | 요청이 둘 이상으로 해석되고 해석에 따라 수정 대상이 달라진다 |
| 2 | 되돌리기 어렵다 (삭제, 마이그레이션, git 이력 변경) |
| 3 | 밖에서 쓰는 약속이 바뀐다 (공개 시그니처, CLI 플래그, API 응답, 설정 키, 파일 형식) |
| 4 | 의존성이 바뀐다 |
| 5 | 요청에 없는 범위가 늘어난다 |
| 6 | 기존 동작이나 테스트를 바꾸거나 지워야 한다 |
| 7 | 보안이나 비용에 닿는다 |
| 8 | 완료 조건을 검증할 방법이 없다 (J1이 0이면 리뷰어가 이 질문을 올린다) |
| 9 | 동등한 설계가 둘 이상이고 선택이 취향이나 제품 판단이다 |

묻지 않는 것은 저장소에서 확인되는 사실, 관례가 답을 정하는 선택, 승인된 계획 안의 구현 세부다.
질문에는 묻는 이유 한 줄, 선택지, 모델이 권하는 답을 붙이고 한 번에 모아서 낸다.
대화형에서는 dcode의 `ask_user`를 쓴다 (`deepagents_code/ask_user.py:368`). 비대화에는 이 도구가 없다 (`Day09/TOOLS_REFERENCE.md:126`).

## 8. Memory

- 위치: `.deepagents/memory/`. 기억 하나에 파일 하나, frontmatter에 이름, 종류, 한 줄 설명.
- `MEMORY.md`는 색인이다. 코드가 각 파일의 frontmatter를 읽어 생성하고 항상 프롬프트에 넣는다. 직접 고치지 않는다.

| 종류 | 내용 | 저장 | 주입 |
|---|---|---|---|
| 프로젝트 규칙 | 어느 작업에나 적용되는 규칙 | 에이전트가 후보를 제안하고 사람이 확인한 뒤 저장. 사용자가 직접 말한 규칙은 바로 저장 | 항상 |
| 작업 기록 | 사용자의 요청, 사용자가 내린 결정, 최종 설계안 | 승인까지 간 계획에서 뽑아 자동 저장. 계획이 없는 요청은 저장하지 않는다 | Jev J6가 1인 것만, 모델 호출 전에 |

- Jev가 놓친 기억은 모델이 색인을 보고 직접 열 수 있다.
- 주입된 기억이 계획의 어디에 반영됐는지는 계획의 "참고한 Memory" 절에 적는다.
- J6 호출 수는 작업 기록 수에 비례한다. 동시에 호출한다.

## 9. 자기 개선

**개선 관찰.** 작업이 끝나면 코드가 실행 기록에서 신호를 센다. 기준을 넘은 신호만 모델이 관찰 문장으로 적는다.
신호는 같은 도구의 같은 오류 반복, 같은 명령의 반복 실행, 리뷰 왕복 상한 도달, J4 거부 수, 테스트 실패 뒤 재시도 수다.
관찰은 프롬프트에 주입하지 않고 개선 단계의 입력으로만 쓴다.

**개선 절차.**

1. 관찰이 기준 이상 쌓이면 알림만 띄운다.
2. 사용자가 명령(가칭 `/improve`)으로 시작한다. 예상 호출 규모를 먼저 알린다.
3. 모델이 개선안을 만든다. 고칠 수 있는 대상은 프로젝트 규칙과 Skills 둘이다.
4. 고정 과제 묶음(3개 안팎)을 개선안 없이 한 번, 넣고 한 번 실행한다.
5. 통과 기준은 `test_command` 전부 통과, 그리고 지표가 나빠지지 않음이다.
6. 검증 결과를 보여주고 사람이 승인하면 반영한다. 떨어진 개선안도 기록은 남긴다.

소스 안의 시스템 프롬프트(`deepagents_code/agent.py:1662`)와 Jev 질문 문구는 개선 대상에서 뺀다.

## 10. 모니터링

- 추적은 Langfuse로 한다. LangSmith는 쓰지 않는다. `langfuse.langchain`의 `CallbackHandler`를 붙인다
  (수업의 사용 예: `Day04_new/cap_lab/experiment.py:33`).
- 요청 하나가 trace 하나다. 단계마다 구간을 둔다. 탐색, 코드 변경 판정, 계획 작성, 리뷰(왕복마다), 사람 질문, 승인, 코드 변경, 테스트, 최종 결과.
- Jev 판정, Memory 주입, 자기 개선은 구간을 직접 열어 입력, 결과, 오류를 적는다.
- 지표는 trace에 값으로 붙인다. 실행 시간, LLM 호출 수, 도구 호출 수, 재시도 수, 리뷰 왕복 수, Jev 거부 수.
- 개선 관찰의 신호는 Langfuse API에서 가져와 센다. 로컬 기록 파일은 두지 않는다.
  작업이 끝나면 전송을 비운 뒤 조회하고, 안 보이면 정해진 횟수만 다시 시도한다. 끝내 안 보이면 그 작업의 관찰은 건너뛰고 알린다.
- 조회 명령을 작게 만든다. 최근 작업 목록과 실패 요약(실패 구간, 오류, 지표) 두 화면이고, 자세한 내용은 Langfuse 주소로 넘긴다.
